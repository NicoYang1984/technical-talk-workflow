# Content Contract｜两稿不只是标题一致

## 每个节点必须有六个对应锚点

1. **核心问题**：上一节为什么自然进入这一节。
2. **唯一关键结论**：离开本节时听众应该能复述什么。
3. **技术锚点**：重要公式、变量范围、优化对象/单位等；允许一个节点只保留一个主要锚点。
4. **固定案例**：输入、操作、输出、数值和图示必须匹配。
5. **视觉位置**：图示真正出现，讲者稿知道“先指哪块，再问什么”。
6. **过渡与时间**：下一问、计划用时、短版出口。

`outline.json` 可在每节增加：

```json
{
  "id":"P07", "title":"Mechanism", "minutes":5,
  "example_id":"toy-v1", "visual_id":"mechanism-map",
  "tier":"core", "transition":"What is missing next?",
  "anchors":{"projection":["important equation"],"notes":["important equation"]},
  "exit_line":"In one sentence..."
}
```

`anchors` 的作用是**故意选择的逐字关键字**，而不是要求两份稿件每句话一字不差。将最容易在版次之间漂移的公式关键词、示例数字、对照对象放入锚点；不同语言的稿件可以分别设置锚点。

## 两稿的文字比例不需要固定

- **投屏**：问题、定义、最少技术展开、例子和转场都可直接看到；不要把一页缩成只剩四个词。
- **Notes**：更口语，允许例子展开和分层备答；不能未经铺垫引入另一套公式/另一个实验数据。
- 发现 Notes 说不顺时先检查叙事，只有真的缺关键前提才回补投屏；不要简单把 Notes 整段贴上屏幕。

## 真实风险：局部更新造成隐性错位

修改 P10 公式后同时检查 P09 的引入和 P11 的承接；更换一张示例图时检查例子设定、投屏文字、Notes 指向和导出页码。更改一个版本应同时更新 `outline.json`, `projection.md`, `speaker_notes.md` 与资源 manifest。

脚本可以检查节点与显式锚点，但无法自动检查语义相同、数学等价、图片文本或语气自然。交付前仍须进行人工交叉对读。
