# Visual & Platform｜图示负责解释而不是装饰

## 图的角色

- **Navigation**：先提供全景，反复高亮当前步骤，结束时回到全景。
- **State transition**：让听众看到一步动作前后哪些变量发生变化；适合网格、时间线、逐步动画。
- **Worked example**：数值、输入条件、公式和结论必须完全一致，不能只凭图“看起来合理”。
- **Boundary/contrast**：两幅图强调一个可决定的差异，如同一机制在不同输入条件下的变化。
- **System map**：明确接口、归属、数据流和故障归因，而不是按名字排列模块。

一张图应填写：`purpose`, `question`, `point_to`, `asset_id`, `fallback`, `source_status`, `rendered_ok`。讲者必须知道点击前问什么、点击后观察什么、如果动画不动如何替代。

## 输出载体判断

| 媒介 | 适合 | 必须小心 |
| --- | --- | --- |
| 飞书文档 | 长技术讲义、表格、公式、团队评论 | 普通代码块通常不渲染 Mermaid；复杂公式、表格跨页需人工验收 |
| Google Docs | 可访问/协作的稿件与备份 | Markdown/LaTeX/HTML 导入不保证数学保真 |
| Markdown / GitHub Pages | 可版本控制的源与交互式网页 | 投屏现场可能需要网络；按需准备静态版 |
| PPT / PDF | 稳定投屏、明确节奏与图示布局 | 过密文本可读性低；分页可能拆开公式、图和表 |

如果现场用的是飞书：Mermaid 需测试原生文本绘图组件或用已渲染的 PNG；HTML 交互独立打开前必须在目标终端试用。任何可交互 Demo 都备一张静态图。

## 最终导出（特别重要）

1. 以**实际展示设备**打开最终文件，而非只看源 Markdown；
2. 查所有页首/页尾：没有孤立标题、跨页截断的关键表头、紧跟下一页才出现的解释图；
3. 核对公式是否按预期渲染、符号没有因转义变形；
4. 检查图片比例、字号、对比度、能否在投影距离识别；
5. 若教程是长文滚动而非分页投屏，检查每一屏是否有自然停顿点和导航锚；
6. 开场打开媒体、备用图片和链接，确保离线也能完成核心讲解。

视觉审核不能只靠程序的文件存在检查。每个核心图至少应有一张人工查看通过的最终效果。
