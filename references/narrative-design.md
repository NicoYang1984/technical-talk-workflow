# Narrative Design｜从知识目录到因果讲解

## 设计顺序

先确定听众带着什么知识来（Known），再找一个他们现在无法回答的关键问题（Gap），最后说明本章提供什么机制（Bridge）。不要把所有预备知识都塞进第一章；按需铺设、边用边讲。

适用问题链：

1. **Why**：问题为何值得解决？已有方式在哪些场景不够？
2. **What**：最小概念与任务边界是什么？
3. **How**：公式、算法或操作流程怎样让目标成立？
4. **Why this design**：为什么不是另一种设计？对应成本、误差或风险是什么？
5. **When in practice**：放到实际系统会出现哪些瓶颈、数据流和失败案例？
6. **What next**：如何验证与讨论？

## 一节的“讲得出来”结构

- 抛问题，先允许听众作出预测；
- 展示最小例子，固定变量与设定；
- 让概念或公式解释例子的结果；
- 辨析相似概念以及类比何时失效；
- 用“这里仍未解决的问题”引出下一节。

**坏转场**：“接下来介绍第二个算法 PPO。”

**好转场**：“现在知道如何把反馈转化为梯度，但一次更新如果改变策略太多，采样的数据还可靠吗？这就引出稳定策略更新的方法。”

## 从直觉到机制的渐进阶梯

公开 LazyAttention 教程给出了一个可迁移的范式：Arange（各做各的）→ Reduce（需要合并）→ BN（形状和计算维度带来新约束）→ Attention（结合输出依赖和 Softmax）→ 两种实现策略 → 真实输入/性能证据。**不要照搬 CUDA 内容**；应在新领域构造同型阶梯：最小无交互例子 → 必须协调/累计的一步 → 新约束让旧方法变慢或失效 → 对照策略 → 实际适用边界。

每一台阶明确写出“新增了什么难点”，不能用术语数量当作深度。核心推导跟随具体输出和数据移动，不独立背一页公式。详见 [机制漫游](mechanism-walkthrough.md)。

## 案例体系

- **主案例 A：直觉可计算。** 最好规模小、可手算、能逐节添加一个假设。
- **桥接小例子：对比机制。** 当新方法依赖与主例不同的设定时，插入一个 1–3 分钟例子即可。
- **主案例 B：工程端到端。** 展示从输入到输出、数据记录、失败和性能约束的真实流向。

同一个概念要提供变量字典：原案例中的对象 → 技术对象 → 工程实现对象；标记“不等价但有启发”的类比边界。

## 图形和交互选择

选择图示不是为了好看，而是为了降低脑内模拟的负担。优先：主流程图（全场导航）、最小数值例子（解释公式）、动画/步进（解释状态变化）、架构图（解释模块边界）、性能图（只用真实数据）。每一个交互控件都要有旁白“点哪一下、预测什么、验证什么”，失败时静态图能替代。

## 讲者角色

不要将“谦虚”变成自我否定。讲者可以坦承不熟悉的生产细节，但对已经验证的公式和例子要准确。面对打断：先用一句话回答当前问题，再指出展开所需假设；可现场改正，必要时把开放问题列入会后核验清单。
